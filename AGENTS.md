# Working in this repo

Keep changes small, clear, and covered by tests.

## Code

- Keep each module focused. If a file grows past about 300 lines, consider splitting it.
- Put app logic in `lib/`, desktop code in `desktop/`, tests in `test/`, and build tools in `scripts/`.
- Keep domain modules in `lib/animation/`, `lib/behavior/`, `lib/i18n/`, `lib/rendering/`, `lib/settings/`, and `lib/protocol/` free of the DOM, timers, and network calls. Pass in time and randomness so behavior is easy to test.
- `lib/host/host-adapter.mjs` is the only module that handles DeepSeek Harness event names. Keep Harness details out of the model and renderer.
- Define animations, skins, and phrases as data. Put user-facing text in the localized `lines.*.mjs` and `ui.*.mjs` files.

## Changes

- Check errors early. Avoid deeply nested logic, but don't split up simple code just to add guards.
- Comments should explain why, not repeat what the code does. Write comments in English.
- Don't hide errors. Make failures visible in the UI, diagnostics, or tests.
- Protect user privacy: never read or store prompt text, responses, tool arguments, or session titles. Don't add telemetry or calls to external services.
- Don't add runtime dependencies without a good reason.
- Don't reformat or rewrite unrelated code.

## Tests and generated files

- Add behavior tests in `test/<module>.test.mjs`. Test results and important guarantees, not implementation details.
- Test core logic deterministically. Use smoke tests for DOM changes and integration tests for HTTP, packaging, and the desktop bridge.
- Add a regression test for behavior changes.
- Don't edit generated bundles or pages by hand. Change their source and rebuild them. If atlas art changes, update the related manifests and `docs/preview`.
- Keep editable source PNGs on `art-source`, not `main`, and leave generated `frames-256/` out of both branches. The source guide in `assets/source/deepseek-chan/README.md` pins the optional source snapshot; normal builds and tests must not fetch it.
- The README's pictures and its GIF set are generated by `scripts/build-preview.mjs` (`npm run preview:art`, needs Pillow). Add the GIF to the data list in that script — never commit a picture by hand. Hand captures live in `docs/preview/captures/`.

## Public surface

`test/package.test.mjs` guards the public package format and metadata:

- the bundle shape: `package.json` name, `main`, `exports`, the `dsh` field, the
  `cordis.patch.yml` rows and the committed `lib/client.js` id,
- package metadata for the registry and for npm: `repository`, `homepage`, `bugs`,
  `license`, `engines`,
- every local link and local image in the English README resolves.

## Checks

Use Node.js 22 or newer. If the test tools are missing, install them with:

```sh
npm install --no-save jsdom esbuild
```

Run the main check:

```sh
npm run check
```

For Rust shell core changes, also run:

```sh
npm run test:core
```

For packaging or release changes, run `npm run verify:release`. For atlas changes, regenerate and check the previews as described in `.github/workflows/ci.yml`.

## When you finish

Say what changed and which checks you ran. Mention if you could not test in DeepSeek Harness or on the target platform.
